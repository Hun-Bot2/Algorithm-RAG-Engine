# Design

The initial executable is a stdlib-only, read-only analysis under research/recommendation_inputs/. It verifies the private run manifest against the committed baseline receipt, verifies stored ranking hashes and matched query/candidate identities, and recomputes top-10 overlap, first-result agreement and candidate concentration. Public outputs contain aggregate statistics and source hashes only. Historical input-generation costs and existing evaluation coverage are carried with explicit attribution. The script does not load raw problem descriptions or vectors.

Matched cohort: admitted publisher descriptions, 8,101 Codeforces and 1,323 AtCoder dataset rows. LeetCode is absent; AtCoder native identities remain unresolved. This is distinct from the 24,303 native-key runtime catalog. Existing full-title neighbor counts are not a three-platform statement benchmark.

Next comparison inputs: title baseline; statement sections with full-token coverage; structured solving idea (technique, state/invariant, transitions, complexity, prerequisites); own solution code/notes; separate-channel fusion. Control query/candidate identities, model, language/preprocessing and policy eligibility. Vary input first; model comparison follows only after input effects are inspectable. Missing sections stay missing, and statements/code are not inferred from titles.

Evaluation uses separately judged dimensions: idea relation, content relation, learner-specific usefulness. Include different-story/same-technique and similar-story/different-technique negatives. Weakness usefulness needs a frozen learner snapshot and a source rationale, so cannot be scored by static pair similarity alone. Display method identity/rank only after blind relevance assessment. Duplicate/family split prevents memorized variants appearing across development/test. New matched pools have new IDs/versions; do not replace the old frozen review pool.

Tradeoff: existing artifacts permit a fast, reproducible input-sensitivity comparison now, but cannot establish accuracy without applicable labels. Do not select a winner by cosine magnitude, agreement, or visually pleasing neighborhoods.

## Read-only inspection viewer
The user requested direct inspection of the comparison. Add a loopback-only, read-only viewer under research/recommendation_inputs/ using the existing admitted publisher corpus and saved top10 results. Validate receipt hashes before loading. Display source and candidate text via textContent, method-specific cosine/TF-IDF scores, source provenance and unknown native IDs. Search the available 9,424-row cohort and compare two methods at a time. The viewer is retrospective inspection, not a labeling system or a new quality evaluation. It does not show quarantined LeetCode statements, load external assets, generate explanations, or persist learner/review state. Tests cover input verification and safe route/identity handling; inspect the real UI with synthetic/allowed local data and preserve statement screenshots privately.

## LeetCode within-platform inspection
Add a separate LeetCode scope to the viewer. Reuse current catalog-v4 cached title vectors (3,053 source problems) and recompute exact cosine against active eligible LeetCode targets only. Compare with native-tag Jaccard as a non-embedding baseline; no zero-overlap or missing-tag candidates are fabricated. Display exact source title, native difficulty, tags and official link; statement_text stays null. This scope must be explicitly distinguished from historical CF↔AtCoder publisher-statement experiments. The offline generator records catalog/key/vector/output hashes in a new receipt and never changes old vector files. Viewer reads a private generated JSON, preserving its stdlib-only runtime. Validate target platform/eligibility/self exclusion, known scores and missing tags; browser-test scope switching and Buddy Strings/Check Distances searches.

## Learning workspace integration
Add a fifth navigation item, 문제 유사도 비교, with a #similarity deep link. The local app proxies an allowlisted GET-only /comparison/ subtree to the session-owned loopback viewer, using a same-origin frame policy; browser APIs resolve relative to the mounted subtree. /api/local/comparison supplies a minimal availability check. The Worker/core imports no Node/research modules and sees an unavailable/retry state if the local tool is absent. The default landing page remains Calendar. The comparison tab defaults to same-LeetCode metadata inspection; publisher experiments remain a separate scope. Existing private corpus/vector data are not copied into hosted/public/ or release assets.

## Second iteration: real input ablations
Two independent cohorts: (1) hash-pinned authored curriculum, 90 problems (60 LeetCode, 20 AtCoder, 10 Codeforces), with title vs rationale vs concept+rationale encodings in the same pinned MiniLM; same-LeetCode and all-platform inspection are separate scopes. (2) admitted publisher statement corpus, with deterministic exact-heading extraction and an intersection cohort requiring a nonempty description/Input/Output. Constraints remain optional and explicitly missing. Reuse original title/full-chunk vectors for baseline inputs, but rerun retrieval on the same selected cohort. New section-text vectors use the same original-token chunk pooling as the baseline. Examples/notes remain in the source view but excluded from the new task-section representation. Record every source index, selected-field token coverage, timing, hash, missingness and scope.

No existing model infers algorithm correctness, mastery, missing strategies or unknown sections. Source-grounded authored rationale text is a compact strategy proxy with explicit missing invariant/complexity fields, not a complete solution proof. Baselines are inspectable references, not recommended policy changes. Actual quality is unavailable until applicable idea/content/usefulness judgments exist.
